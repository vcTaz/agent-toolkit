## Domain and lifecycle definitions

The eight core objects and Assignment/ReviewRecord are frozen dataclasses. Collections use tuples; direct canonical-record constructors reject mutable collections, wrong enums/types and invalid basic values. Role definitions are provider-independent data. AgentGroup contains only routing membership and branch tags. Result, Criterion and Evidence are supporting values, not separate services.

All records have `schema_version=1`, an ID and monotonic revision. Run-owned records carry `run_id`. UTC timestamps are checked. JSON contains a closed `type` discriminator and typed `data`; unknown types, fields and schema versions fail closed.

| Object | Implemented transitions |
|---|---|
| Agent | IDLE → RUNNING or DISABLED; RUNNING → IDLE or DISABLED |
| Task | PENDING → READY, FAILED or CANCELLED; READY → RUNNING, FAILED or CANCELLED; RUNNING → READY, COMPLETED, FAILED or CANCELLED |
| Finding | PROPOSED → CRITIQUED or REJECTED; CRITIQUED → VALIDATED or REJECTED; VALIDATED → INVALIDATED or SUPERSEDED; INVALIDATED → CRITIQUED or REJECTED |
| Assignment | CREATED → RUNNING or CANCELLED; RUNNING → COMPLETED, FAILED or CANCELLED |
| Message | QUEUED → DELIVERED or REJECTED |
| AgentGroup | ACTIVE → CLOSED |
| Role | Immutable versioned configuration; create a new identity for a new version |
| ReviewRecord | Immutable observation targeting an exact revision |
| SwarmState | Immutable snapshot successors; finding classifications and references checked on commit |
| Run | RECEIVED and the planned workflow/terminal enum values are defined. Workflow transitions deliberately refuse execution until the controller/gates are implemented. Counters/revisions may update now. |

Terminal states have no outgoing transitions. New persisted records must start in their initial lifecycle states. `transition()` returns a successor without changing its input. `assign_role()` rejects running agents. `revise_finding()` requires a new ID and points to the predecessor; persisted claim/evidence/dependency content cannot change in place. Assignment provenance is pinned, and review history is append-only. Invalidation returns a set of successor findings with validated dependents invalidated transitively; callers must commit related snapshot changes together.

The snapshot validator checks task/finding DAGs, parent/supersession cycles, references and run ownership, assignment/task consistency, reviewer independence, role versions, one RUNNING assignment per agent/task, message addresses and shared-state classification.

A transition to VALIDATED requires a PASS validation ReviewRecord for the current finding revision, no blocking issues, a different assignment, and host-marked verified tool evidence. Complete-snapshot validation additionally rejects reviews from the generating agent. This is a structural foundation: a future domain-specific verifier must establish that the evidence actually proves the claim. Neither provider agreement nor a fabricated confidence score performs that check.

## Provider and tool interfaces

```python
class ModelProvider(Protocol):
    async def generate(self, request: ModelRequest) -> ModelResponse: ...

class Tool(Protocol):
    spec: ToolSpec
    async def execute(
        self, arguments: dict, execution_context: ExecutionContext
    ) -> ToolResult: ...
```

ModelRequest contains a request ID, immutable normalized messages, tool specifications, an output contract, remaining time and output limit. ModelResponse contains structured JSON content or normalized tool calls, optional usage/provider request ID and finish reason. ProviderError codes are TIMEOUT, TRANSIENT, AUTHENTICATION, UNSUPPORTED and INVALID_RESPONSE. Unexpected adapter errors are converted to execution failures with audit events.

`await execute(context, role, provider, tools, audit=..., budget=...)` executes one assignment with bounded model/tool turns. It never schedules or commits draft findings, messages, reviews, tasks or results. The host supplies the context and authoritative permissions.

ExecutionResult contains `status`, `summary`, `findings`, `messages`, `task_requests`, optional `review`/`result`/`confidence`, plus host-attached assignment ID and tool results. Draft nested structures have explicit allowed fields. Unknown authority fields, malformed JSON, duplicate JSON keys, fabricated tool references and role-incompatible fields are rejected. Review and result references remain proposals for future controller admission; they do not authorize mutations.

Tools available to the model are the intersection of run, agent and role allowlists. The entire tool-call batch is preflighted before any dispatch. Tool arguments/results use a deliberately small validated JSON-schema subset; unsupported keywords fail closed. Arithmetic accepts at most 64 bounded integers and returns `actual` plus `matches`. It never evaluates arbitrary code.

Defaults: 60-second total execution timeout, one output repair, 80 provider requests/120 tool calls per shared Budget, eight calls per response, 16,000-character output, 8,000-character tool payload and 24,000-character execution context. Repairs and tool-loop requests consume budget. Durable run limits can be stricter. Provider errors terminate the execution instead of being automatically retried; future retry policy can distinguish transient errors without hiding accounting.

Async timeout/cancellation is cooperative. Trusted pure tools are not a sandbox for arbitrary untrusted Python. Raw transcripts are not persisted; structured results and bounded tool evidence are audited. The fake provider retains requests in memory to make local scenarios inspectable.

## SQLite storage and atomicity

`SQLiteRepository.commit(run_id, records, events)` opens BEGIN IMMEDIATE, checks optimistic revisions and the complete merged domain snapshot, writes records and events, and commits once. Any invariant or database failure rolls back the complete transaction. A stale/skipped revision raises ConflictError; SQLite failures raise StorageError.

```sql
records (
    run_id TEXT, id TEXT, kind TEXT, revision INTEGER, data TEXT,
    PRIMARY KEY (run_id, id)
)
events (
    run_id TEXT, sequence INTEGER, id TEXT UNIQUE, data TEXT,
    PRIMARY KEY (run_id, sequence)
)
```

Actual columns are NOT NULL. Record `data` is versioned canonical JSON. Event `data` contains schema version, event ID/type/time, run/sequence, applicable task/agent/assignment/role/group IDs, causation/correlation IDs and structured detail JSON. Each changed record needs a matching revision event. Mutation events receive authoritative before/after snapshots from the repository, overriding any caller-supplied change detail. Event sequences are independent per run and allocated inside the transaction; rolled-back writes do not consume a sequence.

RepositoryAudit is a synchronous execution sink. PROVIDER_REQUESTED and TOOL_STARTED update Run counters and persist the event in one transaction before external dispatch. It enforces durable limits even when a caller starts another execution with a fresh in-memory Budget. An unavailable audit store prevents dispatch. Other execution events record response metadata, rejected outputs, tool evidence and final proposals.

`get()` returns a record; `inspect()` returns records, ordered events and completion classification. Nonterminal runs are labeled INCOMPLETE, including unfinished runs opened after interruption. Inspection does not assert that a currently executing run crashed. No resume, replay or external-call exactly-once guarantee is provided. Unknown database schema versions are rejected rather than overwritten.

## Deviations and later-stage implications

- Added the explicitly requested INVALIDATED state and validated-knowledge terminology. AgentGroup remains flat and lightweight.
- Split serialization, value validation, output parsing and durable auditing into focused modules instead of expanding domain.py/execution.py/persistence.py further.
- Used setuptools as the locally available build backend; no runtime dependencies or development-tool downloads were needed. Tests use unittest as approved.
- Run enum states exist, but state-machine execution and success guards remain blocked until the later controller stage. Creating/completing work is not an execution-seam side effect.
- Stored bounded tool evidence directly in structured events. Large artifact storage is not needed for these pure tools; add it only when tool payloads require it.
- Used INCOMPLETE inspection terminology because stored nonterminal state alone cannot distinguish a currently active process from a crashed one.
- Role instances are supplied by the host; nine role names are defined, but a complete prompt catalogue is not needed for the foundation checkpoint.
- Output contracts are Python records plus a compact provider-facing JSON description. There is no duplicate manually maintained schema directory. Tool schemas support only the documented subset.

Before Stage 4, preserve three boundaries: admit proposals against current IDs/revisions and criterion coverage; pin live assignment/context snapshots and reject stale results; use one shared run Budget plus durable accounting. Add cancellation/outcome commits at the controller boundary. Verification policies must bind tool evidence to the exact target claim, and propagate invalidation plus shared-state removals in the same transaction. Keep decomposition, scheduling, budgets, review, stopping, synthesis gating and deterministic propagation policies separate from the controller.

Stage 4 is not started.
